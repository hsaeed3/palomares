# AC conventions used, and how each was verified

| Convention | Used as | Verified against |
|---|---|---|
| kn5 binary layout (v5: header, textures, materials, node tree, 44-byte vertices, u16 indices) | `scripts/p2/kn5.py` | moppius/blender-assetto-corsa-tools exporter source (read, not vendored); our reader round-trips every file to the last byte |
| Axis mapping (east, north, up) → AC (x, y=up, z=−north); triangle order kept; UV v flipped | kn5.py `ac_from_local` | same exporter (`convert_vector3`, `uv = (u, −v)`) |
| Embedded PNG textures | 22_build_kn5.py | exporter embeds PNG when the source isn't DDS |
| Physics by name prefix `1ROAD`, `1GRASS`, `1KERB`, `1WALL` + `surfaces.ini` KEYs | build + data/surfaces.ini | common community practice; **not** checked in-game |
| `models_<layout>.ini` `[MODEL_n] FILE/POSITION/ROTATION` multi-layout folder, `ui/<layout>/ui_track.json` | 22_build_kn5.py | community docs; **not** checked against a downloaded track |
| Spawn locators: Y up, **+Z forward** (row 3 of row-major matrix) | `locator()` in 22_build_kn5.py | AcTools ReadMatrix, moppius exporter, stock Barber AC_START_0 vs AI line (see "Spawn / locator orientation") |
| A-B timing `AC_AB_START_L/R`, `AC_AB_FINISH_L/R` | timing kn5 | CLAUDE.md spec; vanilla support unverified |
| Shaders `ksPerPixel`, `ksPerPixelMultiMap` (road), `ksPerPixelAT` (foliage) | materials | standard Kunos shader names; property sets not checked in-game |

## CSP / Pure (Custom Shaders Patch) track config

- CSP reads per-track settings from `content/tracks/<track>/extension/ext_config.ini` when the
  acc-extension-config repo has no config for the track (`extension/config/tracks/<track>.ini` is the
  global/repo location). Vanilla AC ignores the folder. Source: CUP RainFX docs
  https://cup.acstuff.club/docs/csp/tracks/rainfx
- Foliage: CSP/Pure foliage treatment (translucency, tree wind, tree shading) keys on the Kunos
  `ksTree` shader; community configs switch tree materials with
  `[SHADER_REPLACEMENT_n] MATERIALS=... SHADER=ksTree CULL_MODE=DOUBLESIDED` (ks_nordschleife.ini in
  https://github.com/ac-custom-shaders-patch/acc-extension-config/tree/master/config/tracks).
  `PROP_n = name, value` overrides material values; replacements are applied once at load.
  Source: https://cup.acstuff.club/docs/csp/general/shader-replacements ,
  https://github.com/ac-custom-shaders-patch/acc-extension-config/wiki/Tracks-%E2%80%93-Miscellaneous-options
- `[GRASS_FX]` GRASS_MATERIALS / OCCLUDING_MATERIALS / MASK_BLUR / SHAPE_*; `[RAIN_FX]`
  PUDDLES_/SOAKING_/SMOOTH_/ROUGH_/LINES_MATERIALS (main asphalt in both puddles and soaking);
  `[WIND] DYNAMIC_FLAGS=AUTO`; `[LIGHTING] SPECULAR_MULT/LIT_MULT` — key names copied from
  ks_highlands.ini / ks_nordschleife.ini in acc-extension-config.
- Our kn5 v5 with plain ksPerPixel / ksPerPixelMultiMap / ksPerPixelAT needs no format change for CSP.
- Generated by `scripts/p2/ext_config.py`, called at the end of `22_build_kn5.py` (which wipes the
  track folder); it asserts every material it names exists in MATS.

## Spawn / locator orientation (verified against source code and stock-track data)

**Convention:** a kn5 node matrix is 16 little-endian floats, row-major in the row-vector (DirectX/SharpDX) form: floats 0-2 = local X axis, 4-6 = local Y (up), 8-10 = local Z, 12-14 = translation, 15 = 1. For AC_START_n / AC_PIT_n / AC_HOTLAP_START_n the car faces the dummy's **local +Z** (floats 8-10), with local +X on the car's left (X = Y x Z, a proper right-handed rotation).

Sources:
- AcTools (Content Manager) reads the 64 bytes in order into M11..M44 and takes translation from M41..M43: https://github.com/gro-ove/actools/blob/master/AcTools/ReadAheadBinaryReader.cs (`ReadMatrix`), `AcTools/Kn5File/Kn5Basic.cs`, and `AcTools.Render/Kn5SpecificSpecial/TrackMapRenderer.cs` (`MoveCameraToStart`, AC_START_0 translation).
- moppius/blender-assetto-corsa-tools writes `matrix[col][row]`, i.e. the transpose of Blender's column-vector matrix, with axes converted (x, y, z) -> (x, z, -y): https://github.com/moppius/blender-assetto-corsa-tools/blob/master/exporter/kn5_writer.py (`write_matrix`) and `exporter/exporter_utils.py` (`convert_matrix`, `convert_vector3`). Our `ac_from_local` (E, N, U) -> (E, U, -N) is the same mapping.
- AC-evo converter, measured on Kunos stock tracks: "Spawn dummies point along their local +Z: on Barber AC_START_0's +Z is (0.704, 0, -0.710), the AI line's first step (0.70, -0.70)". It reads position from floats 12-14 and forward from floats 8-10. Stock AC1 cars also have their front at +Z and left at +X (ks_mazda_miata WHEEL_LF at (0.705, 0.285, 1.168)): https://github.com/WhoaThatCombo/AC-evo-content-manager- (`converter/docs/FORMATS.md`, `converter/src/track/scan.rs` `Dummy::forward`).
- AC sets the initial heading from these dummies alone. The layouts ship no ai/fast_lane.ai or spawn ini that could override it.

Status: scripts/p2/kn5.py writes the 16 floats in this order, and `locator()` in scripts/p2/22_build_kn5.py puts the run-direction vector in row 3 (+Z). A re-read of every palomares_timing_*.kn5 shows that row 3 points at the start-gate midpoint (dot >= 0.98) on all 6 segments, northbound and *_rev, and that AB gate L lies on the car's left. **v0.1 (-Z) was backwards. v0.2.0-dev1 (+Z) is correct by every source above.** A further "backwards" report on v0.2 therefore points at the install (an old track folder or CM cache, or the wrong zip) rather than the convention. Ask for a screenshot and the layout name before flipping again.

## Physics meshes (v0.2.0-dev3, scripts/p2/21d_physics.py, collide.py, qa_collisions.py)

| Finding | Source | Status |
|---|---|---|
| Mesh node byte order: class, name, nChildren, active; castShadows, isVisible, isTransparent; vertices (pos, nrm, uv, tangent = 11 f32); u16 indices; materialId, layer, lodIn, lodOut, bsphere centre+radius, **isRenderable**. Our kn5.py matches field-for-field. | gro-ove/actools `AcTools/Kn5File/Kn5Writer.cs` / `Kn5Basic.cs` (read) | verified (code) |
| Physical = name `<digit><KEY>` with KEY in surfaces.ini; plain `WALL…` is not physical. Collision-only walls: separate simple meshes, **renderable=false** (we keep isVisible=true, castShadows=false, lod 0/0, layer 0, a material assigned). | assettocorsamods.net "BIG PROBLEM WITH WALLS" (thread 2061) | community; not tested in-game |
| Wall normals must point **outward / toward the car**; inverted normals let cars drive through; walls should be the simplest geometry, complex physics geometry gets cars stuck. | same thread; Steam RTB discussion (collisions with many polys give odd results) | community |
| Cars bounce off walls side-on but pass through head-on: consistent with penetration resolution along the nearest face. Our dev2 walls were 0.14 m closed boxes, so >7 cm penetration exits through the back face. Fix: away-from-road faces moved 1.2 m back (`collide.thicken_away`), road-side face stays at the visual barrier. | assettocorsamods.net thread 2061 report + our analysis | inferred; please verify in-game |
| Every kn5 in models_<layout>.ini is loaded, physics included (our road/terrain physics already come from separate kn5s and drive). No per-mesh physics triangle limit is documented; the only hard limit is 16-bit indices (≤65535 verts/mesh). | dev2 driving test; AcTools reader | partly verified |
| Terrain: dev2 1GRASS_t* was the raw CDT of the LiDAR DTM: within 25 m of the edge, adjacent-face creases up to 153 deg (fold-overs) and 5.4 m vertex spikes, which is what "glitching into hills" was. 21d smooths heights (Taubin + local crease clamp, stitch pinned). | reports/qa_physics.json | measured |
| Trees had **no collision** (tree meshes non-physical), so the car drove into the trunk/crown and down a steep bank. 21d adds 8-sided closed trunk prisms `1WALL_tree_NN` (≤25 m from the edge). | 21d | fixed |

## AI / ideal line (v0.2.0-dev4, scripts/p2/racing_line.py, ai_spline.py)

- File: `<layout>/ai/fast_lane.ai` per layout (layout folder, next to `data/`), version 7. Layout (little endian):
  4 x i32 header (version=7, point count, lap time, sample count), per point 3 x f32 position (AC world: x, up, -north),
  f32 cumulative length, i32 id; then i32 count and 18 x f32 per point (speed **m/s**, gas, brake, unused lat-g,
  radius, distance to left / right edge, camber, direction, normal xyz, length, forward xyz, tag, grade); then
  i32 hasGrid = 0. Verified against gro-ove/actools `AcTools/AiFile/AiSpline.cs`, `AiPoint.cs`, `AiPointExtra.cs`,
  `AiSplineGrid.cs` and the AC-evo converter (`converter/docs/FORMATS.md`, `src/ac1/ai.rs`: "speed (m/s)",
  "Later data (game caches) is ignored"). Every file is read back and checked in 22 (`ai_spline.read`).
- Point-to-point: the spline runs in the run direction from 30 m before the start gate (covers the spawn) to 30 m
  past the finish gate; speeds are a standing-start GG profile. lapTime/sampleCount 0 (not a recording); AC builds
  its own lookup grid (hasGrid 0). **Not verified in game**: whether AC recomputes the speed/brake payload;
  if the ideal line colours look wrong, re-record in game (AI app) and keep ours as a fallback.
- No `pit_lane.ai` (one pit box, p2p: AC runs without one on many community p2p tracks) and no `ai_hints.ini`
  (CSP-only, optional). Not verified in game.
- Kerbs and brake boards of the `track_*` layouts are derived from the same line (config/kerbs.yaml `placement`,
  config/racing_line.yaml); plots in reports/racing_line/.

## Collision convention (v0.2.0-dev6, FFB-safety rebuild; scripts/p2/collision_conv.py, qa_ffb_safety.py)

User report on dev4/dev5 (FFB wheel): cars glitch through walls, hitting trees/barriers gives violent FFB spikes,
light comes through hills, NVIDIA warnings on load. Findings and the rules now enforced:

| Rule | Source | Status |
|---|---|---|
| Collision is by **mesh name**: `<digit><KEY>...`; AC "only really supports wall type collisions": anything solid is a `1WALL` mesh. Don't put two keywords in one name. | assettocorsamods.net "Build your first track - basic guide" (thread 12); "BIG PROBLEM WITH WALLS" (thread 2061) | community, consistent across sources |
| Walls = **new, separate, simplest-possible invisible meshes** placed along the visual barrier (renderable=false), not renamed visual geometry. Complex wall geometry makes cars get stuck and costs CPU. | thread 2061 (moderator); Steam RTB discussion ("let the invisible Collision Wall handle collisions, the string object can be complex") | community |
| Wall normals point **outward / toward the car**; inverted normals let cars drive through. | thread 2061 | community |
| Two collidable wall objects **must not be close to each other or overlap**. | assettocorsamods.net / GTPlanet AC mods thread (search results 2020-24) | community |
| Seams in physics meshes (merged/split geometry where a wheel can drop) cause wheels dropping/snagging. | GTPlanet AC PC mods general discussion (Imola seam report) | community |
| Trees and small props: community and Kunos tracks give them **no collision**; dense forest is kept out with a smooth invisible boundary wall, not per-trunk colliders. No source documents per-trunk colliders as standard; forum users asking for tree hits find only "invisible walls". | search results above; inspection of the dev4 design | community practice + inference |
| Textures embedded as **DDS with mipmaps**, power-of-two sizes (Kunos kn5s carry .dds). PNG works but has no mips; a 4096x5256 NPOT PNG was in dev5. | moppius exporter (embeds DDS if source is DDS), Kunos content | partly verified (format); the NVIDIA-warning cause is inferred |
| Vertex tangents must be perpendicular to the normal. dev1-5 wrote tangent=+X on every vertex: degenerate TBN on east/west-facing surfaces with normal-mapped shaders. | AcTools Kn5 vertex layout (pos, nrm, uv, tangent) + shader math | inferred |
| Distant terrain (backdrop hills) must cast shadows, otherwise sun shines "through" the hills. dev1-5 had backdrop cast_shadows=False. | measured in the kn5 | fixed |

### What dev6 builds (21d -> collision_conv.rebuild)
- Every per-object 1WALL box from 21b/21c/21e/race_assets is discarded after being used as a *position description*.
- **Barriers, fences, walls, cut banks, crowd barriers**: merged per road side into one offset function; swept as ONE
  welded, closed, invisible slab per side per 250 m chunk (`1WALL_L_NN`, `1WALL_R_NN`): road face at the visual barrier
  face, 1.0 m deep, ground-following, >= 1.6 m tall, smoothed (no creases), flared ends (turn away 0.8 m over 4 m)
  so there is no square corner to snag on. No overlaps or nesting by construction (nearest face wins).
- **Trees: no collision.** A **forest-line wall** (same slab) runs where >= 4 trunks stand within +-10 m along the road
  and <= 14 m past the drivable edge, at the 25th-percentile trunk offset, never closer than 2 m past the edge.
  Guidance for the tree rework: whatever tree models are used, keep them non-physical (no digit prefix); the forest
  line is computed from data/derived/trees.csv (x_local, y_local, ground_z), so it follows the data, not the models.
  If simple colliders are ever wanted, use one smooth wall per forest edge, never per-trunk prisms.
- **Small props** (poles, signs, mailboxes, cones, bales, gantry legs, overhead banners): no collision.
- **Buildings / large solids** (footprint >= 1.8 m): one closed 8-vertex box each, never on the drivable surface.
- `1WALL_start` / `1WALL_end`: one 2 m deep closed box each.
- Flags: visible=True, renderable=False, cast_shadows=False, material `invisible`.
- Gate: scripts/p2/qa_ffb_safety.py (in build.py and `make qa-ffb`) fails the build on: tree/prop colliders, thin
  (< 0.5 m) or short (< 1.2 m) walls, open (non-watertight) wall shells, overlapping colliders, creases > 30 deg on a
  wall's road face, tiny/degenerate/sliver physics tris, NaN, bad normals/tangents, creases on 1ROAD/1KERB,
  terrain creases near the edge, PNG/NPOT/unmipped textures, non-shadow-casting terrain, unknown physics keys.
